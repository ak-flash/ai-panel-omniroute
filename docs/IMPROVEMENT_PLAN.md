# План улучшений AI Panel

Дата аудита: 2026-10-03

## Краткий вывод

Проект уже находится в хорошем состоянии для небольшого production-сервиса: код разделён на маршруты, сервисы, провайдеры и хранилище; секреты не выдаются через публичные DTO; предусмотрены `/api/health`, `/api/ready`, метрики, ограничения auth и защита Host/CORS; CI проверяет lint, форматирование, документацию, секреты, типы, тесты на Node 22/24, Playwright и production-аудит зависимостей.

Основные точки роста — эксплуатационная надёжность, наблюдаемость, расширение контрактных тестов провайдеров, повышение строгости типов и улучшение CI/CD-дисциплины.

## Наблюдения по текущему состоянию

- Серверная композиция сосредоточена в `src/app.js`, маршруты вынесены в `src/routes/`, адаптеры — в `providers/`.
- Хранилище на `sql.js` имеет шифрование AES-256-GCM, master-key, миграции, атомарную запись и статус persistence.
- Конфигурация централизована в `src/config.js`, переменные окружения документируются и проверяются скриптами.
- Есть большой набор unit-тестов, integration-тесты API и Playwright smoke/feature-тесты.
- CI уже запускает `npm run test:ci` с высокими порогами покрытия на Node 24.
- В коде встречаются пустые `catch {}` в фоновых/необязательных операциях. Это допустимо для best-effort сценариев, но затрудняет диагностику, если ошибка важна для эксплуатации.
- `check:types` ограничен частью JavaScript-файлов и использует `strict: false`, `noImplicitAny: false`; это снижает пользу статической проверки для маршрутов и UI.
- Тестовый прогон пишет ожидаемые stack trace в лог, из-за чего локальный результат `npm test` трудно быстро читать; стоит разделить ожидаемые ошибки и реальные сбои.
- В CI есть отдельный `audit`, но не видно автоматической проверки устаревших зависимостей или регулярного smoke-деплоя.

## Приоритеты

### P0 — безопасность и восстановление

#### 1. Формализовать backup/restore encrypted store

**Почему:** `data/store.db` и ключ — критичные данные. Ошибка диска, повреждение файла или неверный порядок восстановления может привести к потере настроек и секретов.

**Что сделать:**

- Добавить официальный скрипт резервного копирования с согласованным набором файлов и проверкой прав доступа.
- Добавить проверку целостности backup и команду тестового восстановления во временный каталог.
- Документировать сценарий восстановления для PM2/systemd/Docker.
- Добавить integration-тест: backup → restore → открытие store с тем же ключом.
- Явно описать правило: backup master key хранится отдельно от backup базы.

**Готово, когда:** восстановление проверяется одной documented-командой и подтверждено автоматическим тестом.

#### 2. Провести security regression для auth, proxy и SSRF-защиты

**Почему:** панель работает с ключами провайдеров и проксирует запросы к внешним URL.

**Что сделать:**

- Расширить тесты на DNS rebinding, IPv4/IPv6, encoded path traversal, неожиданные `Host`/`X-Forwarded-*`, redirect и private-network upstream.
- Добавить матрицу поведения при комбинациях `PUBLIC_ORIGIN`, `TRUST_PROXY`, `AIPANEL_AUTH_TOKEN`, `ALLOWED_HOSTS`.
- Зафиксировать лимиты тела запроса, timeout, размер ответа и поведение при upstream redirect.
- Проверить, что секреты не попадают в ошибки, metrics, access/provider logs и Playwright artifacts.

**Готово, когда:** security-набор запускается отдельно через `npm run test:security` и покрывает все перечисленные граничные сценарии.

### P1 — надёжность production-эксплуатации

#### 3. Улучшить наблюдаемость

**Почему:** сейчас есть агрегированные метрики процесса, но для диагностики провайдеров и proxy этого может быть недостаточно.

**Что сделать:**

- Добавить request correlation ID и возвращать его в заголовке ответа.
- Расширить метрики по маршруту, провайдеру, статусу upstream, cache hit/miss и latency buckets.
- Добавить безопасные structured logs для startup, config validation, store flush, auth failures и circuit-breaker событий.
- Для пустых `catch {}` использовать `debug`/`warn`-события там, где ошибка влияет на readiness, cache или миграцию.
- Добавить документацию по интерпретации `/api/metrics` и типовым alert-порогам.

**Готово, когда:** по request ID можно связать клиентский ответ, server log и upstream failure без раскрытия секретов.

#### 4. Защитить провайдерские запросы circuit breaker/backoff-логикой

**Почему:** недоступность одного внешнего API может создавать повторные всплески запросов и ухудшать UI.

**Что сделать:**

- Ввести ограниченный exponential backoff с jitter для повторяемых сетевых ошибок.
- Добавить per-provider circuit breaker и cooldown.
- Различать ошибки auth, rate limit, timeout, upstream 5xx и invalid response.
- Возвращать фронтенду стабильный machine-readable error code и время следующей попытки.
- Добавить тесты на переходы circuit breaker и сброс после успешного запроса.

**Готово, когда:** временный сбой провайдера не приводит к лавине запросов, а пользователь получает понятное состояние.

#### 5. Проверить graceful shutdown и lifecycle фоновых сервисов

**Почему:** tracker AgentRouter и store требуют корректного завершения при PM2 restart или SIGTERM.

**Что сделать:**

- Добавить integration-тесты на SIGTERM/SIGINT: остановка tracker, flush store, закрытие HTTP-сервера.
- Установить конечный deadline shutdown и логировать незавершённые операции.
- Проверить поведение при startup failure и частично открытом store.
- Сверить readiness с фактической готовностью всех обязательных зависимостей.

**Готово, когда:** restart не теряет последнюю запись и не оставляет активные таймеры/handle'ы.

### P1 — качество кода и контрактов

#### 6. Расширить типизацию за пределы текущего include

**Почему:** `check:types` проверяет только отдельные server/provider-файлы и работает в нестрогом режиме.

**Что сделать:**

- Постепенно включить `src/routes/**/*.js`, `src/app.js`, `src/auth.js`, `src/security.js` и shared DTO.
- Добавить JSDoc-типы для config, provider contract, request context, store API и error payload.
- Включать `strict` поэтапно, начиная с новых/изменяемых модулей.
- Рассмотреть миграцию наиболее контрактно-критичных модулей на TypeScript только после стабилизации границ.

**Готово, когда:** публичные API-модули проверяются типами, а provider adapters реализуют единый проверяемый контракт.

#### 7. Сделать единый контракт провайдера и contract-test suite

**Почему:** число адаптеров растёт, а расхождения в полях usage/models/auth могут ломать UI.

**Что сделать:**

- Описать нормализованные схемы usage, models, errors и capability flags.
- Запускать общий contract suite для всех адаптеров с mock upstream.
- Добавить тесты на malformed JSON, missing fields, pagination и rate limits.
- Версионировать внутренний provider DTO или ввести schema validation на границе.

**Готово, когда:** добавление нового провайдера требует прохождения общего набора тестов, а не только отдельных тестов адаптера.

### P2 — CI/CD и сопровождение

#### 8. Улучшить CI-проверки

**Что сделать:**

- Добавить `npm run test:security` как отдельный обязательный job или шаг.
- Добавить проверку `npm outdated`/Dependabot policy с контролируемым расписанием.
- Кэшировать Playwright browser binaries либо явно документировать стоимость установки.
- Добавить проверку размера артефактов и retention policy для логов/отчётов.
- Добавить smoke-проверку запуска production-команды с минимальным env (`AIPANEL_ENV_FILE=none`).
- Сохранять coverage summary как CI artifact.

**Готово, когда:** pull request проверяет функциональность, security, типы, форматирование, документацию и запуск production-процесса.

#### 9. Ввести release checklist и версионирование схемы store

**Что сделать:**

- Добавить `docs/RELEASE.md` с шагами: `npm ci`, проверки, backup, миграции, restart, `/api/ready`, rollback.
- Явно хранить версию схемы базы и тестировать последовательные миграции.
- Описать совместимость Node.js, lockfile и production-зависимостей.
- Для breaking changes провайдеров добавить changelog entry.

**Готово, когда:** новую версию можно выпускать и откатывать по короткой воспроизводимой инструкции.

### P2 — интерфейс и пользовательский опыт

#### 10. Добавить единый frontend state для loading/error/refresh

**Что сделать:**

- Унифицировать состояния загрузки, пустых данных, stale cache, rate limit и auth expiration.
- Показать пользователю время последнего успешного обновления и причину stale-данных.
- Добавить retry с backoff вместо бесконтрольного повторения.
- Проверить клавиатурную навигацию, focus management диалогов и контраст в основных сценариях.
- Расширить Playwright-тесты на offline/timeout, истёкшую сессию и ошибку upstream.

**Готово, когда:** каждая основная страница имеет предсказуемое состояние loading/success/empty/error и покрыта хотя бы одним e2e-сценарием.
