# Стратегия тестирования

## Уровни

### Unit

Команда: `npm run test:unit`.

Проверяет чистую клиентскую логику, registry и адаптеры провайдеров. HTTP-вызовы
адаптеров направляются только на локальные mock-upstream серверы. Тесты не
требуют сети, пользовательских секретов и существующей базы данных.

Файлы:

- `test/http.test.js`;
- `test/model-match.test.js`;
- `test/providers-registry.test.js`;
- `test/security.test.js`;
- `test/xkiro-adapter.test.js`;
- `test/agentrouter-adapter.test.js`.

### Integration

Команда: `npm run test:integration`.

Проверяет HTTP-контракт `createApp`, работу encrypted store во временном
каталоге, Antigravity OAuth/quota flow с локальным Google mock и CLI smoke.

Файлы:

- `test/server.test.js`;
- `test/antigravity.test.js`.

### Полный прогон

Команда: `npm test`.

Последовательно запускает unit и integration. Любое исправление контракта API,
хранилища, OAuth или provider adapter должно сопровождаться regression-тестом
на наиболее узком подходящем уровне.

## Покрытие

Команда: `npm run test:coverage`.

Используется встроенный coverage-инструмент Node.js без отдельной зависимости.
Baseline от 2026-08-29: 95,23% строк, 81,94% ветвей и 90,13% функций по
отчёту `all files`. Показатели служат диагностикой, а не формальной целью: новый
код должен прежде всего покрывать значимые ветви и ошибки, а не увеличивать
процент за счёт малоценных тестов.

## Стиль и форматирование

Отдельный formatter/linter пока не вводится, чтобы не смешивать массовое
переформатирование с функциональным рефакторингом. До выбора инструмента:

- сохранять стиль изменяемого файла и не форматировать соседний код без причины;
- использовать `'use strict'`, `const`/`let`, точку с запятой и одинарные кавычки
  в новых серверных модулях и тестах;
- проверять проект диагностикой редактора и полным `npm test`;
- вводить автоматический lint/format отдельным изменением после декомпозиции,
  когда его diff не скроет изменения поведения.

## Изоляция

- не обращаться к реальным API провайдеров;
- не читать пользовательские `.env` и `data/settings.db`;
- использовать свободные локальные порты и временные каталоги;
- закрывать серверы и store в `finally`/test teardown;
- не делать тесты зависимыми от порядка запуска.
