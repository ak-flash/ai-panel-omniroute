# Encrypted store: данные, ключи, восстановление

Хранилище панели — один SQLite-файл, в котором каждое значение зашифровано
AES-256-GCM master-ключом панели. Ключи шифрования БД и самих значений не
покидают сервер (кроме клиентских полей, которые клиент сам прислал и которые
сервер пишет в хранилище, но обратно не отдаёт).

## Где лежат данные

| Путь | Что это |
| --- | --- |
| `data/store.db` | база настроек (SQLite, значения зашифрованы) |
| `data/store.db.key` | master-ключ, если не задан через окружение |

Каталог `data/` не коммитится — скопируйте оба файла при переносе/бэкапе.

## Master-ключ: приоритет источников

1. **`AIPANEL_MASTER_KEY`** в окружении (рекомендуется на сервере; см.
   `.env.example`). Позволяет перенести базу на другой сервер вместе с env.
2. **Файл `<db>.key`** (по умолчанию `data/store.db.key`, права `0o600`),
   создаётся автоматически при первом запуске.
3. Если ни env, ни файла нет — генерируется новый ключ (и пишется в файл).

Ключ — 32 байта в hex (64 символа). Невалидный формат отклоняется на старте с
ошибкой `bad_master_key` — процесс завершается, а не стартует «полудохлым».

## Формат шифрования (v1)

Каждое значение хранится в колонке `value` таблицы `kv` в виде:

```
v1:<iv b64>:<tag b64>:<data b64>
```

AES-256-GCM, IV 12 байт, тег аутентичности 16 байт. Формат байт-в-байт
совместим с реализацией до этапа 4 — существующие базы читаются без миграции
данных.

## Проверочная запись

В базе есть внутренняя запись `__verify` — известная строка
`ai-panel-store-ok`, зашифрованная master-ключом. Она не видна через `get` и
`snapshot`, но позволяет при открытии базы мгновенно отличить:

- **wrong_key** — ключ не подходит: не расшифровывается ни одна запись;
- **corrupted** — база побита: не расшифровывается часть записей (или
  проверочная запись при читаемых данных).

Базы, созданные до введения проверочной записи, мигрируют автоматически: при
первом открытии с правильным ключом `__verify` дописывается. С неверным ключом
миграции не происходит (иначе «чужой» ключ можно было бы навязать базе).

## Схема ключей (allowlist)

Публичный API хранилища принимает только ключи из `STORE_KEYS`
(`src/store/index.js`): ключи провайдеров (`xkiroKey`, `agentrouterKey`,
`agentrouterUserId`), OmniRoute (`omniUrl`, `omniKey`), Antigravity
(`agRefreshToken`, `agProject`, `agEmail`), настройки UI и служебные снимки
(`aliases`, `comboActive`, `dlgProvider`, `modelsProvider`,
`statsProvider`, `agentrouterDayBalance`), `notificationThresholds`,
`activeAccount` (имя активного аккаунта для multi-account credentials,
RFC-0003).

Произвольное имя записать нельзя — попытка вернёт `unknown_key`. Чтение
(`snapshot`) терпимо к унаследованным записям из старых версий.

## Multi-Account Credentials (RFC-0003)

Начиная с версии 2026-09-03 в базе есть вторая таблица — `credentials` —
для хранения credentials нескольких профилей (аккаунтов) на каждый
провайдер. Это позволяет держать, например, два xKiro-аккаунта или
несколько OmniRoute-инстансов и переключаться между ними без
перезапуска панели.

### Структура

```sql
CREATE TABLE credentials (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  account_name TEXT NOT NULL,           -- псевдоним, [a-z0-9_-]{1,32}
  provider_id TEXT NOT NULL,            -- xkiro | agentrouter | omniroute | antigravity
  credential_type TEXT NOT NULL,        -- api_key | user_id | oauth_refresh | url | key | ...
  encrypted_value TEXT NOT NULL,        -- v1:<iv>:<tag>:<data> (AES-256-GCM)
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE(account_name, provider_id, credential_type)
);
CREATE INDEX idx_credentials_account ON credentials(account_name);
```

Каждое значение зашифровано тем же master-ключом, что и поля в `kv`. Секреты
наружу не возвращаются — только булевы `has*` поля и `account_name`.

### Лимиты

- Имя аккаунта: 1–32 символа из `[a-z0-9_-]`.
- Максимум 10 аккаунтов в базе.
- Внутри одного аккаунта один провайдер может иметь несколько полей:
  `agentrouter` — `api_key` + `user_id`; `antigravity` — `oauth_refresh` +
  `project_id` + `email`; `omniroute` — `url` + `key`.

### API

См. `src/routes/accounts.js` и раздел 11.1 плана. Эндпоинты
`/api/accounts`, `/api/accounts/:name`, `/api/accounts/active`.

### Миграция с плоских ключей

При первом открытии базы с новой версией, если в `kv` есть
`xkiroKey`/`agentrouterKey`+`agentrouterUserId`/`omniUrl`+`omniKey`/
`agRefreshToken`+`agProject`+`agEmail`, они переносятся в аккаунт
`default`. Legacy-ключи в `kv` остаются для обратной совместимости
(старый фолбэк в `/api/providers/:id/*`), но новый API использует только
таблицу `credentials` + поле `activeAccount`.

## Гарантии записи

- `setMany()` — батч-транзакция: все ключи валидируются до применения,
  частичного набора настроек не бывает (используется `PUT /api/config`).
- Диск обновляется через очередь: один экспорт БД, запись в `*.tmp`,
  затем атомарный rename. Крашеный процесс не оставляет половину файла.
- `flush()` дожидается попадания изменений на диск, `close()` идемпотентен.
  После `close()` любая операция возвращает `store_closed`.

## Коды ошибок

| Код | Когда возникает | Что делать |
| --- | --- | --- |
| `bad_master_key` | ключ не 64 hex (env/файл/аргумент) | исправить `AIPANEL_MASTER_KEY` / `<db>.key` |
| `wrong_key` | при открытии не расшифровывается ни одна запись | вернуть правильный ключ (см. приоритет выше) |
| `corrupted` | не расшифровывается часть записей или `__verify` не совпадает | восстановить базу из бэкапа |
| `unknown_key` | запись под именем вне `STORE_KEYS` | использовать ключи схемы |
| `store_closed` | операция после `close()` | lifecycle-ошибка, проверить порядок закрытия |

`src/main.js` печатает код и понятное сообщение при старте и завершает
процесс с кодом 1 — сервер не поднимается поверх негодной базы.

## Бэкап и восстановление

```sh
# Бэкап: скопировать пару файл + ключ (при остановленном сервере либо после flush)
cp data/store.db backup/store.db.bak
cp data/store.db.key backup/store.db.key.bak

# Восстановление: скопировать оба файла обратно и перезапустить
```

Требование: ключ и база должны быть одной пары. База без ключа бесполезна,
ключ без базы читает «чужие» данные — и то и другое обнаружится при старте
(`corrupted` / `wrong_key`).

## Ротация master-ключа

Скрипт перешифровывает все записи; если хотя бы одна не читается старым
ключом — выходит без изменений (база не портится).

```sh
# ключ лежит в файле <db>.key — новый запишется туда же
node src/store/rotate-key.js

# ключ в окружении — новый печатается в stdout, добавить в env
AIPANEL_MASTER_KEY=<старый> node src/store/rotate-key.js

# задать новый явно
node src/store/rotate-key.js --new <64 hex>

# другая база
node src/store/rotate-key.js --db /path/to/store.db
```

После ротации перезапустите панель.
