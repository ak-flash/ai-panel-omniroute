# Runbook — эксплуатация AI Panel

Краткие инструкции по диагностике и восстановлению. Справка по хранилищу:
`docs/STORE.md`; архитектурные решения: `docs/DECISIONS.md`.

Сервер слушает `127.0.0.1` по умолчанию (переопределяется `HOST`/`PUBLIC_ORIGIN`),
логи пишутся в файловый логгер с `requestId` у каждого запроса.

## 1. Неверный master key (`wrong_key`)

**Симптом:** при старте сервер завершается с кодом 1; в логе — «master key не
подходит» / `wrong_key`. База не открыта, данные не тронуты.

**Причина:** `AIPANEL_MASTER_KEY` не совпадает с тем, которым шифровалась БД
(другая машина, другой профиль, опечатка в env).

**Действия:**

1. Проверьте, что переменная задана и не содержит лишних пробелов/кавычек.
2. Найдите прежний ключ (менеджер секретов, backup окружения). Подходящий ключ
   восстанавливает доступ без потерь.
3. Ключ утерян — данные восстановить невозможно (AES-256-GCM). Варианты:
   - восстановить БД из backup, зашифрованного доступным ключом (см. `docs/STORE.md`);
   - начать с пустой базы: удалить/переместить файл БД и задать новый ключ,
     затем заново ввести настройки провайдеров.
4. Ротация ключа на живой базе: `node src/store/rotate-key.js` (см. `docs/STORE.md`).

**Не делайте:** повторных попыток «подбора» ключа против рабочей БД — при
неверном ключе открытие детерминированно падает с `wrong_key`, но файл лучше
не трогать до решения.

## 2. Повреждённая база (`corrupted`)

**Симптом:** при старте — ошибка `corrupted`; сервер не открывает хранилище.

**Причина:** обрыв записи (нечистое завершение процесса, сбой диска),
повреждение файла БД.

**Действия:**

1. Сохраните повреждённый файл в сторону для анализа — не перезаписывайте.
2. Восстановите последний backup (процедура и расположение — `docs/STORE.md`).
3. Backup отсутствует — начните с чистой базы (новый файл БД + master key) и
   заново введите настройки; история расходов провайдеров доступна в их
   кабинетах (xKiro dashboard, agentrouter.org/console).

Профилактика: регулярный backup файла БД; записи в БД идут атомарно
(tmp + rename), но от дисковых сбоев атомарность не спасает.

## 3. OAuth invalid_grant (Antigravity)

**Симптом:** в карточке Antigravity — `token_expired`; в логах от Google —
`invalid_grant`.

**Причина:** refresh-токен отозван (выход пользователя, смена пароля,
превышен срок неактивности Google) либо время на машине заметно расходится.

**Действия:**

1. Проверьте системное время (расхождение > нескольких минут ломает OAuth).
2. Получите новую пару токенов и обновите её в Настройках → Antigravity
   (токен хранится в памяти сервера / зашифрованном store, наружу не отдаётся).
3. После обновления — обновите карточку квот; при успехе статус-бейдж исчезает.
4. Если ошибка повторяется сразу — токен отзывается на стороне Google:
   перегенерируйте токен в том источнике, откуда он был взят.

## 4. Недоступный upstream (`provider_error` / 502)

**Симптом:** карточка провайдера показывает `provider_error` (сеть/таймаут) или
`bad_response` с диагнозом «Провайдер вернул не-JSON ответ (HTTP X, Y)».

**Причина:** сеть/DNS, таймаут (xKiro/AgentRouter — 20 c, Antigravity — 15 c),
CDN/WAF-заглушка вместо JSON, отказ upstream.

**Действия:**

1. `GET /api/health` — панель жива; `GET /api/ready` — store/tracker готовы;
   `GET /api/metrics` — счётчики запросов, ошибок (5xx) и средняя задержка.
2. В логе по `requestId` найдите запись запроса; сообщение содержит
   HTTP-статус и content-type upstream, тело заглушки — одной строкой в лог
   сервера (по сниппету видно Cloudflare/WAF/страницу провайдера).
3. `upstream_timeout` — провайдер не отвечает в пределах таймаута: проверьте
   доступность сайта провайдера из этой сети (прокси/файрвол могут резать
   исходящие).
4. Не-JSON с HTTP 200 у AgentRouter — временная заглушка CDN: запрос
   автоматически повторяется до 3 попыток; если повторяется постоянно —
   проблема на стороне сайта, ждите.
5. Убедитесь, что ключ/токен валидны: 401 от upstream показывается как
   `unauthorized` с подсказкой (для AgentRouter — нужен System Access Token
   и User ID, API-ключ sk-… не подходит).

**Не делайте:** не выкладывайте в issue/логи ключи и токены — они в логи не
попадают (`safeLog` отфильтровывает такие поля), не добавляйте их вручную.
