# Архитектурные решения

## ADR-001: Node.js 22 как официальная версия

- Статус: принято.
- Дата: 2026-08-29.
- Решение: разработка и CI используют Node.js 22 LTS; `engines.node` сохраняет
  минимальную совместимость с Node.js 18 до отдельного решения о её повышении.
- Причина: проект использует встроенный `fetch`; единая LTS-версия делает
  локальные и CI-прогоны воспроизводимее.

## ADR-002: local-only по умолчанию

- Статус: принято, техническое ограничение запланировано на этап 1.
- Дата: 2026-08-29.
- Решение: штатный сервер слушает loopback. Remote-режим должен включаться
  явно и только вместе с аутентификацией, allowlist CORS и TLS reverse proxy.
- Причина: приложение хранит и использует секреты провайдеров, поэтому открытый
  сетевой периметр несовместим с моделью персональной локальной панели.

## ADR-003: отказаться от поддержки `file://`

- Статус: принято.
- Дата: 2026-08-29.
- Решение: UI поддерживается только через HTTP-сервер приложения.
- Причина: server-side vault и API являются обязательной частью продукта;
  отдельный файловый режим дублирует поведение и ослабляет модель безопасности.

## ADR-004: остаёмся на sql.js вместо нативного SQLite

- Статус: принято.
- Дата: 2026-08-30.
- Решение: хранилище продолжает работать на sql.js (WASM SQLite) с очередью
  атомарных записей; нативный `node:sqlite` не подключаем.
- Причина: объёмы персональной панели (десятки записей, один писатель) далеки
  от ограничений sql.js; нативный модуль дал бы нулевой выигрыш, но добавил бы
  различия окружений (сборка/версия Node) и ещё одну причину для различий
  локальной и серверной установки. Переход возможен в рамках компонента
  `persistence.js`, если требования к объёму/конкурентности появятся.

## ADR-005: формат v1, проверочная запись и allowlist ключей

- Статус: принято.
- Дата: 2026-08-30.
- Решение: формат шифрования значений фиксируется как `v1:<iv>:<tag>:<data>`
  (AES-256-GCM) без изменения относительно доэтапной реализации; при открытии
  базы ключ подтверждается проверочной записью `__verify` (legacy-базы
  мигрируют при первом успешном открытии); запись ограничена allowlist
  `STORE_KEYS`.
- Причина: байт-совместимость избавляет существующие инсталляции (включая
  продакшн-базу на VPS) от миграции данных; проверочная запись делает ошибку
  ключа и повреждение базы диагностируемыми при старте вместо тихих пустых
  настроек; allowlist закрывает запись произвольных ключей через публичный API.

## ADR-006: фронтенд — vanilla ES-модули без сборки

- Статус: принято.
- Дата: 2026-08-30.
- Решение: фронтенд остаётся без фреймворка и бандлера; код разделён на
  ES-модули в `public/js/` (общая инфраструктура + `pages/<page>.js` как
  entry каждой страницы), подключение — один `<script type="module">`.
- Причина: браузерные ES-модули решают задачу этапа 5 (изоляция
  инфраструктуры и page-specific логики) без нового инструментария;
  отдельный entry на страницу исключает загрузку чужой логики, а отсутствие
  шага сборки сохраняет простоту деплоя (статика раздаётся как есть).
