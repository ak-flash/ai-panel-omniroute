# Интерпретация /api/metrics

`GET /api/metrics` (требует auth) возвращает агрегаты с момента старта процесса
или последнего `resetMetrics()`. В метриках нет URL, request ID и секретов —
только счётчики.

## Поля

| Поле             | Тип    | Что означает                                                             |
| ---------------- | ------ | ------------------------------------------------------------------------ |
| `requests`       | number | Общее число обработанных HTTP-запросов                                   |
| `errors`         | number | Число ответов со статусом ≥ 500                                          |
| `avgDurationMs`  | number | Средняя длительность запроса, мс                                         |
| `statuses`       | object | Счётчик по HTTP-статусу (`"200"`, `"404"`, …)                            |
| `latencyBuckets` | object | Гистограмма latency: `le100`, `le500`, `le1000`, `le5000`, `gt5000` (мс) |
| `routes`         | object | Счётчик запросов по шаблону маршрута (`/api/accounts`, …)                |
| `providers`      | object | Обращения к провайдерам по имени (`agentrouter`, …)                      |
| `cache`          | object | `hit` / `miss` — попадания кэшей (TTL-кэш ответов)                       |

## Типовые alert-пороги

Значения подобраны для одиночного инстанса; настройте под свой трафик.

| Метрика                                     | Предупреждение                        | Критично       | Комментарий                                                           |
| ------------------------------------------- | ------------------------------------- | -------------- | --------------------------------------------------------------------- |
| `errors / requests` (5xx ratio за окно)     | > 2%                                  | > 5%           | Рост обычно связан с upstream; сверяйте с `providers`                 |
| `statuses["429"]`                           | рост в 2 раза за 10 мин               | > 10% запросов | Rate limit от провайдеров — проверьте лимиты ключей                   |
| `statuses["401"]`/`statuses["403"]`         | любой непрерывный рост                | —              | Подбор ключей или истёкший ключ; смотрите `auth_login_failed` в логах |
| `avgDurationMs`                             | > 1000 мс                             | > 5000 мс      | Деградация upstream или таймауты; сверяйте с latencyBuckets           |
| `latencyBuckets.gt5000 / requests`          | > 5%                                  | > 15%          | Много очень медленных запросов — timeouts upstream                    |
| `providers[p]` при открытом circuit breaker | событие `circuit_breaker_open` в логе | —              | Провайдер недоступен; cooldown по умолчанию 30 с                      |
| `cache.hit / (hit + miss)`                  | < 30% при стабильном трафике          | —              | Низкая эффективность кэша; проверьте TTL и повторяемость запросов     |

## Как связать метрики с логами

1. По `statuses` и `providers` найдите всплеск ошибок по конкретному провайдеру.
2. В логах найдите соответствующее structured-событие (`circuit_breaker_open`,
   `provider_circuit_blocked` и т.п.) — в ответе клиенту при этом
   `error: 'provider_circuit_open'` и `retry_after_ms`.
3. По request ID из заголовка ответа `x-request-id` найдите конкретный запрос
   в server-логе (ID не попадает в метрики).
