## 1. Резюме

Фундамент у проекта крепкий: секреты write-only, шифрованное хранилище, строгий CSP для
скриптов, 236 тестов, CI из пяти job'ов. Но с 8 сентября CI на `main` красный, все проверки
после линтера не запускаются, и за это время накопились ошибки:

1. **CI не работает 17 пушей подряд** — `lint:docs` читает удалённые `docs/*.md`; тесты,
   Playwright и `npm audit` в CI пропускаются. Порог покрытия 95 % при этом ничего не проверяет.
2. **Один некорректный HTTP-запрос роняет сервер** (`GET http://[`).
3. **Режим отладки из `.env.example` ломает все карточки провайдеров**
   (`TypeError: log.info is not a function`).
4. **Риски потери данных:** после одной ошибки записи хранилище перестаёт сохранять изменения;
   ротация master key портит учётные данные аккаунтов; ключ, изменённый в «Настройках», после
   перезапуска игнорируется.
5. **Периметр:** в remote-режиме (`PUBLIC_ORIGIN`) нет аутентификации, в локальном режиме
   проходит DNS rebinding.

Порядок работ — в разделе 6: сначала вернуть CI и устранить падения (1–2 дня), затем периметр и
целостность данных, потом архитектура провайдеров и фронтенд.

## 3. Сильные стороны — сохранить

- Секреты write-only: API отдаёт только флаги `has*`, расшифрованные ключи в браузер не уходят.
- AES-256-GCM со случайным IV на каждое значение; проверочная запись отличает `wrong_key` от
  `corrupted`; неверный ключ останавливает старт.
- Allowlist ключей хранилища, сериализованная запись через временный файл и `rename`.
- CSP без inline-скриптов, `nosniff`, `frame-ancestors 'none'`; защита статики от path
  traversal; лимит тела 2 МБ; `x-request-id`; внутренние ошибки не уходят клиенту.
- URL OmniRoute берётся только из хранилища; proxy не следует редиректам и пробрасывает только
  allowlist заголовков; OAuth `state` одноразовый и с TTL.
- `createApp` получает зависимости параметрами; одна runtime-зависимость (`sql.js`); адаптеры —
  фабрики, легко тестируются моками.
- Фронтенд без сборки, в основном `textContent`, нативный `<dialog>`, ARIA-вкладки, skip-link,
  `prefers-reduced-motion`, темы на OKLCH-токенах без мигания.

## 5. Проблемы и решения

### P0 — сломано или критично

#### P0-1. CI красный с 8 сентября, тесты в CI не запускаются

- **Где:** `scripts/check-docs.js:21-27`, `.github/workflows/ci.yml` (job'ы `check`, `smoke`,
  `security`, `deps` зависят от `lint`).
- **Факт ✅:** коммит `4dbe5c5` удалил `docs/*.md`, а `check-docs.js` читает их без проверки
  существования → `ENOENT`. Падает шаг `npm run lint:docs`, поэтому Node-матрица, Playwright,
  security-тесты и `npm audit` не выполнялись ни разу за 17 пушей (последний зелёный запуск —
  `83dff43`, 2026-09-08).
- **Решение:** переписать `check-docs.js` под текущую документацию: переменные из
  `.env.example` ↔ таблица README ↔ переменные, которые реально читает код; список провайдеров
  в README ↔ `providers/index.js`. Убрать ссылки на `docs/*` (`README.md:150`) и проверку
  раздела «Baseline HTTP-контракта». В CI снять жёсткую цепочку `needs: lint`, чтобы падение
  одной проверки не скрывало результаты остальных.

#### P0-2. Порог покрытия 95 % ничего не проверяет

- **Где:** `package.json`, скрипт `test:ci`.
- **Факт ✅:** `--test-coverage-include='src/**/*.js,public/js/**/*.js'` Node воспринимает как
  один glob с запятой: в отчёт не попадает ни один файл, «all files» = 100 %. С исправленными
  флагами — строки 90,98 %, ветви 78,84 %, функции 90,91 %, то есть порог сейчас провалился бы.
  `providers/` в include нет вовсе. Слабые места: `src/store/rotate-key.js` (64 % строк, 25 %
  функций), `src/metrics.js` (57 %), `src/fetch-utils.js` (67 %), `src/main.js` (72 %),
  `providers/google-oauth.js` (77 %), ветви `providers/experiential.js` (41 %).
- **Решение:** передавать флаг отдельно на каждый glob (`src/**/*.js`, `providers/**/*.js`,
  `public/**/*.js`), выставить пороги по факту (90/78/90) и поднимать их вместе с новыми тестами.
  Страницы фронтенда (`public/js/pages/*`, `dialog.js`) unit-тесты не загружают — их закрывают
  Playwright-сценарии (P2-9).

#### P0-3. Один некорректный запрос роняет процесс

- **Где:** `src/router.js:33`, `src/http.js:109`, `src/app.js:162-164`.
- **Факт ✅:** на `GET http://[ HTTP/1.1` `new URL()` бросает исключение в `dispatch`, затем ещё
  раз в `handleError` внутри `.catch()` — unhandled rejection, процесс завершается с кодом 1.
  Некорректная `%`-последовательность в параметре пути даёт 500 вместо 400 (`src/router.js:44`).
- **Решение:** разбирать URL один раз в безопасной обёртке и отвечать 400; сделать
  `handleError` и access-лог неспособными бросить исключение; добавить в `src/main.js`
  обработчики `unhandledRejection` и `uncaughtException` с записью в лог; регрессионные тесты с
  «сырыми» запросами через `net.connect`.

#### P0-4. Режим отладки ломает все карточки провайдеров

- **Где:** `src/main.js:102`, `src/app.js:62-64`; вызовы `log.info` в `providers/xkiro.js:52`,
  `agentrouter.js:127`, `openrouter.js:64`, `selora.js:63`, `antigravity.js:43`; `.env.example:19`.
- **Факт ✅:** адаптеры получают `providerLogger.log.bind(providerLogger)`, а у связанной функции
  нет свойства `.info`. При `AIPANEL_PROVIDER_DEBUG=true` любой запрос к провайдеру падает с
  `TypeError: log.info is not a function` (HTTP 500). В `.env.example` флаг включён, а README
  предлагает скопировать этот файл.
- **Решение:** передавать объект логгера целиком и нормализовать интерфейс в одном месте; в
  `.env.example` поставить `false`; тест «каждый адаптер с `debug: true`».

#### P0-5. После одной ошибки записи хранилище перестаёт сохранять изменения

- **Где:** `src/store/persistence.js:41-47`.
- **Факт ✅:** `writeChain = writeChain.then(...)` без обработки ошибки: после первого сбоя (нет
  места, права, занятый путь) каждая следующая запись возвращает ту же ошибку и не выполняется,
  даже когда причина устранена. Изменения живут только в памяти и пропадут при перезапуске.
- **Решение:** обрабатывать ошибку на каждом звене очереди, помечать базу «грязной» и повторять
  запись; ошибку писать в лог и отражать в `/api/ready` (P1-3).

#### P0-6. Remote-режим без аутентификации

- **Где:** `src/security.js:66` (единственная проверка — `Origin`), `src/security.js:145`
  (`PUBLIC_ORIGIN` включает bind на `0.0.0.0`); `remoteMode` вычисляется, но нигде не
  используется; пример nginx в `README.md:52-59` без авторизации.
- **Риск 🔎:** любой, кто достучался до сервера, может перезаписать ключи (`PUT /api/config`),
  удалить аккаунты и слать запросы через `/proxy/*` и `/omniroute/*` с сохранёнными ключами.
  Подменив URL OmniRoute, можно получить его management-ключ на свой хост
  (`src/routes/omniroute.js:134`). Bind на `0.0.0.0` открывает порт 8765 в обход reverse proxy,
  если его не закрывает firewall.
- **Решение:** обязательный секрет (`AIPANEL_AUTH_TOKEN`) → страница входа → сессионная cookie
  `HttpOnly; Secure; SameSite=Strict`, сравнение через `crypto.timingSafeEqual`, ограничение
  частоты попыток входа; отказ стартовать в remote-режиме без секрета. В README — рекомендация
  слушать `127.0.0.1` за proxy и пример закрытия порта.

#### P0-7. DNS rebinding: чужой `Host` проходит проверку

- **Где:** `src/security.js:29`, `src/security.js:58`.
- **Факт ✅:** без `PUBLIC_ORIGIN` «свой» origin вычисляется из заголовков `Host` и
  `X-Forwarded-Host` самого запроса. Запрос с `Host: evil.example:8765` и
  `Origin: http://evil.example:8765` получает `/api/config`. Сайт, чей домен перепривязан на
  `127.0.0.1`, может читать и менять настройки; насколько это блокируют защиты браузеров от
  запросов в локальную сеть, зависит от браузера.
- **Решение:** allowlist значений `Host` (loopback, хост из `PUBLIC_ORIGIN`, опциональный
  список) с ответом 421 на остальные; доверять `X-Forwarded-*` только при явном
  `TRUST_PROXY=true`.

### P1 — безопасность и целостность данных

#### P1-1. Два источника правды для ключей провайдеров

- **Где:** `src/routes/providers.js:32-39` (сначала берётся ключ активного аккаунта),
  `src/store/accounts.js:342-367` (однократное копирование ключей из настроек в аккаунт
  `default`), `src/routes/config.js:97-104` (UI пишет только в настройки),
  `src/agentrouter-tracker.js:38-41` (трекер читает только настройки).
- **Риск 🔎:** после перезапуска смена или удаление ключа в «Настройках» перестают действовать —
  наверх уходит старый ключ из аккаунта. Миграция пропускает `experiential`; удалённый аккаунт
  `default` воссоздаётся при старте; UI для аккаунтов нет.
- **Решение:** одна функция `resolveCredential(providerId)` для маршрутов, трекера и
  `/api/config`; `PUT /api/config` пишет «насквозь» в активный аккаунт. Если мультиаккаунты не
  нужны — удалить этот слой. Регрессионный тест «смена ключа после перезапуска».

#### P1-2. Ротация master key портит учётные данные аккаунтов

- **Где:** `src/store/rotate-key.js:44-56` перешифровывает только таблицу `kv`, а таблица
  `credentials` зашифрована тем же ключом (`src/store/accounts.js:257`, `:282`).
- **Риск 🔎:** после ротации база открывается, но `getActiveCredential` падает с `corrupted`, а
  `catch {}` в `src/routes/providers.js:48` это скрывает. Ротацию ничто не защищает от
  параллельно работающего сервера (он перезапишет файл), новый ключ пишется в `<db>.key`
  неатомарно.
- **Решение:** перешифровывать и проверять все зашифрованные таблицы; lock- или pid-файл; запись
  `<key>.new` → `fsync` → `rename`; тесты (сейчас покрыто 25 % функций модуля).

#### P1-3. `/api/ready` всегда отвечает 503

- **Где:** `src/app.js:81-91`.
- **Факт ✅:** проверяется `store.exec`, которого у фасада хранилища нет; `tracker.isRunning` и
  `antigravityService.checkHealth` тоже не существуют. Мониторинг будет считать сервис неготовым
  всегда. `/api/ready` и `/api/metrics` не покрыты тестами.
- **Решение:** готовность = хранилище открыто + последняя запись успешна (P0-5) + трекер
  запущен; тесты на оба эндпоинта.

#### P1-4. «Потрачено сегодня» в AgentRouter обнуляется при каждом перезапуске

- **Где:** `src/agentrouter-tracker.js:74` — при старте `snapshotDayBalance()` вызывается
  безусловно, вопреки комментарию на строках 53-56.
- **Решение 🔎:** при старте та же проверка «снимок за сегодня уже есть»; единая таймзона
  границы суток (трекер берёт локальное время сервера, Experiential и `usage_daily` OpenRouter —
  UTC); внедряемые часы `now` для тестов.

#### P1-5. Таймауты, ретраи и повтор POST при failover

- **Где:** `src/fetch-utils.js:28-34`, `src/proxy.js:30`, `src/routes/omniroute.js:144-155`.
- **Факт ✅:** таймер снимается сразу после заголовков: `fetchJson` с таймаутом 300 мс завершился
  через 1,5 с, медленное тело может висеть бесконечно. `fetchWithRetry` нигде не используется,
  ретраев на 429/5xx нет, `Retry-After` не учитывается.
- **Риск 🔎:** при таймауте proxy (30 с) failover OmniRoute повторяет запрос на резервном URL —
  в том числе `POST /v1/chat/completions` из проверки модели в combo, что может дать двойную
  генерацию.
- **Решение:** таймер до конца чтения тела (`AbortSignal.timeout` или общий бюджет на запрос);
  ретраи с backoff и учётом `Retry-After` только для идемпотентных методов; failover — только
  для идемпотентных методов или при ошибке соединения.

#### P1-6. Гонка и потеря данных при редактировании combo

- **Где:** `public/js/pages/combo.js:539-547` (после `await` нет проверки, что выбрана та же
  combo), `:220-226`; `public/js/settings.js:47-58` (`vaultSet` при ошибке только пишет в
  консоль).
- **Риск 🔎:** при быстром переключении combo на медленной сети данные combo A записываются в
  combo B. Если список выключенных моделей не сохранился, выключение модели удаляет её из
  OmniRoute без возможности вернуть.
- **Решение:** игнорировать ответы для уже не выбранной combo (счётчик запросов или
  `AbortController`); `vaultSet` возвращает ошибку, и PUT в OmniRoute тогда не выполняется;
  PUT'ы выполнять последовательно.

#### P1-7. Тесты используют реальные `.env`, `data/` и `logs/`

- **Где:** `test/helpers.js:217-222` (`startServerProcess` запускает `server.js` с `cwd`
  репозитория и текущим окружением), `src/store/index.js:27` (жёсткий путь `data/`),
  `src/main.js:59` (жёсткий путь `logs/`).
- **Факт ✅:** `npm test` создаёт в корне репозитория `data/store.db`, `data/store.db.key` и
  `logs/ai-panel.log`.
- **Риск 🔎:** на машине разработчика тест откроет рабочее хранилище с его `.env`, а
  стартовавший трекер сразу запросит баланс AgentRouter реальным ключом и запишет снимок.
- **Решение:** переменные `AIPANEL_DATA_DIR`, `AIPANEL_LOG_DIR` и способ отключить чтение `.env`
  (по образцу уже существующей `AIPANEL_CODING_CACHE_PATH`); в тестах — временный каталог
  (`fs.mkdtemp`).

#### P1-8. Цены и балансы: единицы и «неизвестно = 0»

- **Где:** `providers/openrouter.js:187-198` и `public/js/pages/models.js:223`;
  `providers/experiential.js:60`; `providers/openrouter.js:122-127`;
  `providers/selora.js:99-102`, `:160-161`; `providers/agentrouter.js:27`.
- **Риск 🔎 ❓:** OpenRouter отдаёт цены в USD за токен, адаптер передаёт их как есть, а UI
  печатает `toFixed(2)` — платные модели выглядят как `0.00`, сортировка по цене теряет смысл.
  Тестовые данные (`prompt: 0.5` в `test/openrouter.test.js:79`) ошибку маскируют. Отсутствующие
  значения баланса и цен превращаются в 0 («бесплатно», «$0»). `QUOTA_PER_UNIT = 500000`
  захардкожен.
- **Решение:** нормализовать цены в «USD за 1M токенов» с явными именами полей
  (`*_usd_per_1m`); для неизвестных значений возвращать `null` и показывать «—»; тестовые данные
  с реальными порядками величин; сверить с живым ответом `/api/v1/models`.

#### P1-9. Жизненный цикл OAuth Antigravity

- **Где:** `src/antigravity-service.js:91-109`, `:197-235`; `providers/google-oauth.js:103-105`;
  `src/routes/antigravity.js:36`.
- **Риск 🔎:** параллельные запросы запускают несколько refresh одновременно; токен не
  обновляется заранее; любые 400/401 (включая `invalid_client`) трактуются как `invalid_grant`;
  без `GOOGLE_CLIENT_ID` генерируется ссылка входа с пустым `client_id`.
- **Решение:** один общий in-flight refresh, обновление за минуту до истечения, разбор поля
  `error` из ответа Google, понятная ошибка «OAuth не настроен».

#### P1-10. HTML-инъекция в диалоге настроек

- **Где:** `public/js/dialog.js:67-72` (`showResult` пишет в `innerHTML`); вызовы с
  `err.message`, `data.plan`, `saved.message` и пользовательским вводом — строки 329, 363, 405,
  437, 460, 464, 487, 491, 509, 523, 527, 569, 585, 599, 611, 625.
- **Риск 🔎:** CSP блокирует скрипты, но ответ скомпрометированного провайдера или OmniRoute
  может внедрить разметку и стили (поддельные ссылки и кнопки). Функции экранирования во

- **Решение:** собирать сообщения через `textContent` и DOM-узел иконки; правило
  `eslint-plugin-no-unsanitized`; затем убрать `style-src 'unsafe-inline'` из CSP
  (`src/security.js:7`), заменив inline-стили (`public/index.html:220`, `public/combo.html:65`,
  `:81`, `public/partials.js:246`, `:276`, `public/icons.js:60`) классами.

#### P1-11. Явная длина тега AES-GCM

- **Где:** `src/store/crypto.js:66-71` — `createDecipheriv` без `authTagLength`.
- **Риск 🔎:** Node 22 принимает укороченный тег (от 4 байт), что ослабляет аутентификацию
  шифртекста. Это поведение объявлено устаревшим (DEP0182): в Node 24 оно даёт runtime-
  предупреждение, в Node 26 удалено.
- **Решение:** `{ authTagLength: 16 }` и проверка длины тега; в следующей версии формата —
  привязка значения к имени ключа через AAD, чтобы записи нельзя было переставить местами.

#### P1-12. Остановка сервера и надёжность файлов

- **Где:** `src/app.js:176-178` (`store.close()` не ожидается), `src/main.js:135-139` (по
  таймауту 5 с выход с кодом 0), `src/store/persistence.js:45-47` (нет `fsync`, фиксированное
  имя `.tmp`).
- **Риск 🔎:** незавершённая запись при остановке; права на базу и логи зависят от `umask`
  (файл ключа уже пишется с `0600`).
- **Решение:** shutdown ждёт `server.close` и `store.close()`, при таймауте — код 1 и запись в
  лог; `fsync` перед `rename`; явные права `0600` на базу и логи, `0700` на `data/` и `logs/`.

## 8. Чего не делать сейчас

- Не переходить на фреймворк или сборщик фронтенда: ~4,9 тыс. строк JS решаются декомпозицией
  модулей.
- Не менять `sql.js` на нативный SQLite: данных мало; сначала починить очередь записи и ротацию.
- Не вводить TypeScript со сборкой — достаточно JSDoc и `checkJs`.
- Не добавлять управление процессами с сервера до аутентификации: это удалённое выполнение
  команд.
- Не переписывать страницы целиком — выносить по одной карточке с тестами.

## 9. Критерии готовности плана

- CI зелёный, все job'ы запускаются на каждый PR, падение одной проверки не скрывает остальные.
- Порог покрытия охватывает `src/`, `providers/`, `public/` и не ниже факта; цель — 90 % строк
  и 85 % ветвей.
- Нет известных способов уронить процесс одним запросом; некорректный ввод покрыт тестами.
- Remote-режим требует аутентификации; `Host` проверяется по allowlist.
- У ключей провайдеров один источник правды; ротация ключа покрыта тестами.
- README актуален: провайдеры, переменные, эксплуатация (бэкап, восстановление, ротация).

## Приложение А. Как повторить проверки

```bash
npm ci
npm run lint && npm run stylelint && npm test
npm run lint:docs        # сейчас падает: ENOENT docs/BASELINE.md
npm run format:check     # сейчас: 93 файла с замечаниями
npm audit --omit=dev

# Реальное покрытие: флаг include — по одному на каждый glob
node --test --experimental-test-coverage \
  --test-coverage-include='src/**/*.js' \
  --test-coverage-include='providers/**/*.js' \
  --test-coverage-include='public/**/*.js'
```

Падение на некорректной строке запроса (P0-3) — только на тестовом экземпляре:

```bash
printf 'GET http://[ HTTP/1.1\r\nHost: x\r\n\r\n' | nc 127.0.0.1 8765
```
